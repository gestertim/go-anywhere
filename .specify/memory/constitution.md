# Go Anywhere Constitution

## Core Principles

### I. 核心體驗優先
Go Anywhere 的開發 MUST 優先支援建立旅程、新增與編輯行程項目、時間軸及地圖。
可用性與資料正確性不得為裝飾性動畫或非核心效果讓步。每項變更都 MUST 說明其對核心旅程流程的價值。

### II. 資料正確性與持久性
成功儲存的旅程、行程及相關資料 MUST 在重新整理或重新開啟應用程式後保持可用。
日期分組與時間排序 MUST 是確定性的，並以自動化測試驗證。時間軸與地圖 MUST 始終代表同一份底層行程資料，預訂檢視不得建立第二份行程資料。

### III. 預設隱私
旅程 MUST 預設為私人資料。資料層 MUST 強制執行擁有者授權，存取控制不得只依賴隱藏 UI。
系統 MUST 防止使用者存取其他使用者的旅程資料，且不得在公開日誌或錯誤訊息中暴露敏感的使用者或旅程資訊。

### IV. 優雅降級
地圖是行程規劃的增強功能，不是讀取行程資料的必要依賴。地圖供應商不可用時，時間軸與行程詳情 MUST 仍可使用。
任何第三方服務失敗都不得讓使用者無法存取核心旅程資訊；失敗狀態 MUST 清楚說明可用的替代操作。

### V. 清楚的產品狀態
重要互動 MUST 明確處理載入、空內容、成功完成、可恢復失敗及網路失敗狀態。
儲存失敗時，系統 SHOULD 在可行時保留使用者已輸入的表單資料，並提供重試方式。狀態文字與錯誤訊息 MUST 可讓使用者理解下一步。

### VI. 核心行為測試
自動化測試 MUST 覆蓋旅程建立、行程建立、行程編輯、行程刪除、日期分組、時間排序、依日期篩選地圖，以及時間軸與地圖同步。
每次發布前 MUST 至少有一項端對端測試覆蓋主要旅程流程。未涵蓋核心行為的變更不得宣稱已完成。

### VII. 清楚的領域邊界
Trip、Itinerary Item、Place、Booking 及 Note MUST 保持可辨識且分離的領域概念，跨概念的資料責任必須有明確歸屬。
團隊 MUST 避免只為假設中的未來能力建立額外架構；新增抽象必須由目前的複雜度、重複或可測試性需求提出理由。

### VIII. 不提前擴張平台
V1 MUST 不因 AI 行程產生、社群功能、付款、即時協作或公開分享而引入架構複雜度。
這些能力若日後納入，必須透過獨立規格、影響評估與相容性設計處理，不得以未使用的預留結構污染核心領域。

### IX. 向後安全的資料變更
任何資料結構或儲存格式變更 MUST 考慮既有使用者旅程，並提供可驗證的相容、遷移或回復策略。
變更不得在沒有必要理由的情況下使既有成功儲存資料失效；資料遷移失敗 MUST 不得靜默遺失使用者資料。

### X. 行動優先品質
雖然 Go Anywhere 是 Web App / PWA，設計與實作 MUST 以旅客使用手機為主要互動情境。
介面 MUST 優先提供可讀內容、實用的觸控目標、響應式版面與低互動成本；核心操作不得依賴精確滑鼠操作或大型螢幕。

## 額外限制

- 預設產品語言為繁體中文；新增面向使用者的文字 MUST 維持一致的語言與術語。
- 旅程、行程項目、地點、預訂與筆記的資料模型 MUST 支援局部完成狀態，不得因非核心欄位缺漏而不合理地丟棄使用者輸入。
- 日誌、監控與錯誤回報 MUST 採資料最小化原則，不得記錄不必要的個人資料、預訂識別資訊或完整旅程內容。
- 任何外部地圖或網路服務 MUST 具有明確的逾時、錯誤與替代流程，且不得成為時間軸可用性的單點故障。

## 開發工作流程

- 每項功能變更 MUST 先定義可驗收的使用者情境，再實作並補上對應測試。
- 變更審查 MUST 檢查核心體驗、資料正確性、授權、失敗狀態、行動裝置可用性及向後相容性。
- 觸及共享資料或跨檢視同步的變更 MUST 包含整合測試；觸及主要使用者流程的變更 MUST 更新或維持端對端測試。
- 發布品質門檻為：核心自動化測試通過、至少一項主要流程端對端測試通過、無未處理的資料遺失風險，且已驗證載入、空狀態與可恢復錯誤。

## Governance
<!-- Example: Constitution supersedes all other practices; Amendments require documentation, approval, migration plan -->

本憲章優先於與其衝突的慣例。所有功能規格、實作計畫、程式碼審查與發布檢核 MUST 驗證本憲章的適用原則。

修訂程序如下：提出修訂理由與影響範圍，更新本檔案及同步影響報告，執行文件與相關測試檢核，並由專案維護者核准後生效。若修訂影響既有資料或使用者流程，必須附上遷移或回復方案。

版本遵循語意化版本：移除或重新定義既有原則時增加 MAJOR；新增原則或大幅擴充治理要求時增加 MINOR；澄清文字、修正錯誤或非語意性調整時增加 PATCH。每次修訂 MUST 更新最後修訂日期與版本理由。

每次發布前，維護者 MUST 進行憲章合規審查，確認核心測試、隱私授權、資料持久性、錯誤降級及行動優先品質均有證據支持。若無法符合原則，必須在發布前記錄例外、風險、補救期限與負責人。
