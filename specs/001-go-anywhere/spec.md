# 功能規格：Go Anywhere 旅行行程規劃器

**功能分支**：`001-go-anywhere`

**建立日期**：2026-08-13

**狀態**：草稿

**輸入**：使用者描述：建立「Go Anywhere」，一款以行動裝置優先、可作為 PWA 使用的個人旅行行程規劃器，預設語言為繁體中文。

## 使用者情境與測試

### 使用者故事 1 - 建立並管理私人旅程 (優先級：P1)

旅客可以建立一趟旅程，填寫標題、目的地、開始日期與結束日期，之後能編輯或刪除旅程，讓所有相關行程集中在同一個私人空間中。

**為何是此優先級**：旅程是所有行程、預訂與筆記的容器；沒有旅程就無法產生核心價值。

**獨立測試**：建立一趟含完整基本資料的旅程，重新開啟應用程式確認資料仍在，接著修改並刪除該旅程，驗證每一步都能完成且刪除前需要確認。

**驗收情境**：

1. **假設** 使用者位於旅程清單，**當** 輸入標題、目的地、開始日期與結束日期並儲存，**則** 新旅程出現在清單中。
2. **假設** 使用者已建立旅程，**當** 修改基本資料並儲存，**則** 清單與旅程工作區顯示更新後的資料。
3. **假設** 使用者選擇刪除旅程，**當** 尚未完成刪除確認，**則** 旅程不會被刪除；完成確認後，旅程及其行程資料一併不再顯示。
4. **假設** 使用者重新載入或重新開啟應用程式，**當** 儲存成功的旅程存在，**則** 使用者仍可看見該旅程。

### 使用者故事 2 - 建立與維護行程項目 (優先級：P1)

旅客先選擇行程類型，再填寫與該類型相關的標題、日期、時間、地點、地址、座標、備註及可選的預訂資訊；旅客可以儲存未完成的項目，稍後編輯、補完或刪除。

**為何是此優先級**：行程項目是旅客用來回答「今天去哪裡、下一站是什麼、何時發生」的核心資料。

**獨立測試**：逐一選擇六種行程類型，建立至少一個項目，驗證欄位依類型出現；編輯、補充、儲存與刪除各項目，驗證資料正確保留。

**驗收情境**：

1. **假設** 使用者在旅程中新增行程，**當** 先選擇航班、住宿、交通、景點、餐廳或其他其中一種，**則** 只顯示該類型需要或適合填寫的欄位。
2. **假設** 使用者填寫類型、日期、時間、標題、地點與備註，**當** 儲存成功，**則** 行程項目出現在該旅程中。
3. **假設** 使用者只填寫部分資料，**當** 儲存成功，**則** 系統保留該未完成項目，並允許稍後補完。
4. **假設** 使用者編輯已存在的項目，**當** 修改資料並儲存，**則** 所有檢視使用更新後的資料。
5. **假設** 使用者刪除重要行程項目，**當** 尚未完成確認，**則** 項目仍保留；完成確認後才從旅程、地圖與預訂檢視移除。
6. **假設** 使用者輸入的儲存動作失敗，**當** 顯示錯誤，**則** 已輸入的內容仍在畫面上，且使用者可重試。

### 使用者故事 3 - 以每日時間軸掌握旅程 (優先級：P1)

旅客開啟旅程工作區後，可以按日期查看行程；同一天的項目依日期與時間排序，時間、標題、類型、地點及重要預訂狀態優先呈現，詳細資料則可在詳情頁查看。

**為何是此優先級**：時間軸是旅客在旅途中快速理解當日安排與下一個行程的主要方式。

**獨立測試**：建立跨多天、含相同日期不同時間及未填時間的行程，逐日切換並確認分組、排序、空狀態與詳情內容。

**驗收情境**：

1. **假設** 旅程有多天行程，**當** 使用者選擇某個日期，**則** 只顯示該日的項目，並按時間由早到晚排列。
2. **假設** 項目沒有開始時間或結束時間，**當** 顯示時間軸，**則** 項目仍會出現，並以清楚方式表示時間未完成。
3. **假設** 使用者選擇時間軸項目，**當** 開啟詳情，**則** 可查看該項目的完整資料與預訂資訊。
4. **假設** 選定日期沒有任何項目，**當** 使用者查看時間軸，**則** 顯示清楚的每日空狀態與新增行程入口。

### 使用者故事 4 - 在時間軸與地圖之間切換 (優先級：P1)

旅客可以在同一個旅程工作區切換時間軸與地圖；兩者使用同一份行程資料，切換時保留目前日期，地圖標記可開啟與時間軸相同的行程詳情。

**為何是此優先級**：旅客需要同時理解時間順序與地理位置，且切換不應造成上下文遺失。

**獨立測試**：在某日期建立含座標與不含座標的項目，從時間軸切換到地圖並選取標記，再切回時間軸，驗證日期、資料與詳情連結一致；模擬地圖服務失敗後確認時間軸仍可使用。

**驗收情境**：

1. **假設** 使用者正在時間軸查看特定日期，**當** 切換到地圖，**則** 地圖仍以該日期為目前日期，並只顯示該日且有有效座標的項目。
2. **假設** 使用者在地圖選取行程標記，**當** 開啟詳情，**則** 顯示與時間軸選取同一個行程項目的詳情。
3. **假設** 使用者從地圖切回時間軸，**當** 返回完成，**則** 原本選定的日期仍然有效。
4. **假設** 項目沒有有效座標，**當** 使用者查看地圖，**則** 該項目不顯示標記，但仍正常出現在時間軸與其他檢視中。
5. **假設** 地圖服務不可用或載入失敗，**當** 使用者開啟地圖，**則** 顯示可理解的錯誤狀態與替代提示，且時間軸仍可存取及使用。

### 使用者故事 5 - 集中查看預訂與旅程筆記 (優先級：P2)

旅客可以在旅程工作區查看含有重要預訂資料的航班、住宿等項目，也可以儲存與旅程相關的簡單筆記。

**為何是此優先級**：預訂與筆記是旅途中重要的輔助資訊，但必須建立在可靠的行程資料之上。

**獨立測試**：建立含預訂資訊與不含預訂資訊的行程，確認預訂檢視只彙整前者；新增、修改、重新開啟旅程筆記並驗證資料保留。

**驗收情境**：

1. **假設** 旅程中有航班或住宿等含預訂資訊的項目，**當** 使用者開啟預訂檢視，**則** 看見集中整理的預訂資料，且每筆資料可回到原行程詳情。
2. **假設** 旅程中沒有預訂資訊，**當** 使用者開啟預訂檢視，**則** 顯示清楚的空狀態，不建立虛假的資料副本。
3. **假設** 使用者在筆記檢視輸入內容並儲存，**當** 儲存成功後重新開啟旅程，**則** 筆記仍可查看與編輯。

### 邊界情況

- 開始日期晚於結束日期時，系統必須阻止儲存並說明如何修正。
- 日期、標題等部分欄位缺漏時，允許符合「未完成項目」定義的行程保存，並明確標示尚待補完的資訊。
- 行程只有日期沒有時間時，仍須出現在正確日期；多個項目時間相同時，須穩定顯示且不可遺漏。
- 座標缺漏、格式無效或位置無法定位時，行程仍須可在時間軸、預訂與詳情中使用。
- 旅程或行程清單載入中時，需顯示載入狀態且避免使用者誤以為資料為空。
- 網路中斷、讀取失敗或儲存失敗時，需保留可保留的使用者輸入並提供重試方式。
- 刪除旅程或重要行程項目時，取消確認不得造成任何資料變更。
- 使用者嘗試存取不屬於自己的旅程時，系統不得洩露旅程是否存在或其內容。
- 小螢幕、較長標題、較長地址與繁體中文文字不得互相遮蓋或破壞主要操作。

## 需求

### 功能需求

- **FR-001**：系統 MUST 以繁體中文作為預設產品語言，並在手機尺寸下提供可完成核心工作的介面。
- **FR-002**：使用者 MUST 能建立旅程，並提供旅程標題、目的地、開始日期與結束日期。
- **FR-003**：使用者 MUST 能編輯及刪除自己的旅程；刪除旅程前 MUST 要求明確確認。
- **FR-004**：系統 MUST 將旅程及其行程資料預設視為私人資料，並只允許資料擁有者存取。
- **FR-005**：使用者 MUST 能在旅程中建立、編輯及刪除行程項目。
- **FR-006**：建立行程項目前，系統 MUST 讓使用者先從航班、住宿、交通、景點、餐廳及其他六種項目類型中選擇一種。
- **FR-007**：系統 MUST 依所選類型顯示相關欄位，不得以一個未分流的表單要求使用者處理所有欄位。
- **FR-008**：行程項目 MUST 支援類型、標題、日期、開始時間、結束時間、地點名稱、地址、可用時的座標、備註及可選預訂資訊。
- **FR-009**：系統 MUST 允許使用者儲存部分完成的行程項目，並清楚標示可稍後補完的資訊。
- **FR-010**：重要行程項目刪除前 MUST 要求明確確認；取消確認 MUST 保留項目。
- **FR-011**：旅程工作區 MUST 提供時間軸、地圖、預訂及筆記四個檢視，其中時間軸與地圖為同等重要的主要檢視。
- **FR-012**：時間軸 MUST 依日期分組並依時間排序行程項目，且優先顯示時間、標題、類型、地點及重要預訂狀態。
- **FR-013**：時間軸 MUST 提供行程詳情入口，讓完整資料不必全部擠在時間軸卡片中。
- **FR-014**：地圖 MUST 使用與時間軸相同的行程資料，並只顯示目前日期且具有有效座標的項目。
- **FR-015**：地圖與時間軸切換 MUST 保留目前選定日期；地圖標記 MUST 能開啟與時間軸相同的行程詳情。
- **FR-016**：沒有座標的行程 MUST 仍正常出現在時間軸、預訂與詳情檢視；地圖服務失敗 MUST 不得阻止時間軸存取。
- **FR-017**：預訂檢視 MUST 彙整含有重要預訂資訊的現有行程項目，不得建立第二份行程資料。
- **FR-018**：筆記檢視 MUST 讓使用者儲存、查看及編輯與旅程相關的簡單筆記。
- **FR-019**：系統 MUST 提供清楚的空狀態、載入狀態、儲存錯誤、網路錯誤、地圖服務錯誤及刪除確認狀態。
- **FR-020**：儲存失敗時，系統 MUST 保留使用者已輸入的資料並提供重試；成功儲存的旅程、行程與筆記在重新載入或重新開啟後 MUST 可恢復。
- **FR-021**：所有成功儲存的資料 MUST 在時間軸、地圖、預訂、筆記及詳情檢視間維持一致。
- **FR-022**：V1 MUST 不包含購買航班、住宿或活動、AI 自動產生完整行程、即時多人協作、公開分享、社群動態、公開排名、旅遊創作者功能、完整預算、進階旅遊文件管理或付費訂閱。

### 關鍵實體

- **旅程**：使用者建立的私人旅行容器，包含標題、目的地、開始日期、結束日期、行程項目與旅程筆記。
- **行程項目**：旅程中的單一活動或預訂，包含類型、標題、日期時間、位置、座標、備註、完成狀態及可選預訂資訊。
- **預訂資訊**：附屬於行程項目的重要預約或確認資料，供預訂檢視集中呈現，不是獨立的第二份行程。
- **旅程筆記**：附屬於旅程的簡單文字內容，可被儲存、查看與編輯。
- **使用者**：旅程與其資料的擁有者；只能存取自己的私人資料。

## 成功標準

### 可衡量成果

- **SC-001**：新使用者在手機裝置上可於 2 分鐘內建立一趟包含標題、目的地與日期的旅程。
- **SC-002**：在已有旅程的情況下，使用者可於 90 秒內建立一個包含類型、日期、標題、地點與備註的行程項目。
- **SC-003**：在包含 100 個行程項目的旅程中，所有日期分組與時間排序結果皆正確，且使用者不會遺漏任何項目。
- **SC-004**：至少 95% 的測試使用者可在不需外部說明的情況下，於時間軸與地圖間切換並保留正確日期。
- **SC-005**：地圖服務不可用的測試情境中，100% 的使用者仍可從時間軸查看既有行程與詳情。
- **SC-006**：儲存成功後重新載入或重新開啟應用程式，100% 的測試資料可被正確恢復；儲存失敗時 100% 的測試情境保留輸入內容供重試。
- **SC-007**：100% 的未授權存取測試不得顯示其他使用者的旅程內容或敏感資料。
- **SC-008**：至少 90% 的測試使用者可在 30 秒內從旅程工作區找到下一個行程的時間與地點。

### 成功標準驗收協議

- SC-001 與 SC-002 使用固定的手機 viewport、預先建立的測試帳號與一致的測試資料；計時從主要操作入口出現開始，到成功狀態與目標資料出現為止。
- SC-004 與 SC-008 的「測試使用者」至少包含 10 位受測者；不得提供流程外的操作說明，任務完成率分別須達 95% 與 90%。每位受測者的成功/失敗、完成時間與裝置均須記錄。
- SC-003、SC-005、SC-006 與 SC-007 以自動化測試的完整案例集判定，成功條件為所有案例通過。

## 假設

- 使用者以個人身分使用服務，系統已有或將提供能識別資料擁有者的登入或存取機制；具體驗證方式留待實作規劃決定。
- V1 的筆記以單一旅程文字筆記為主，不要求複雜格式、附件或多人共同編輯。
- 座標由使用者或可用的地點資料提供；系統不保證每個地點都能取得座標。
- 預訂資訊是使用者手動保存的行程附屬資料；V1 不要求自動匯入航空公司、飯店或第三方確認信。
- 使用者通常在有網路時操作；離線或網路不穩時至少須清楚顯示狀態、保留未送出的輸入並允許重試。
- 日期與時間依旅程所在地的當地語意顯示；V1 使用 `YYYY-MM-DD` 與 `HH:mm`，不處理跨時區轉換或跨午夜自動推導。
- 產品預設使用繁體中文；本規格不要求 V1 同時提供其他語言。
